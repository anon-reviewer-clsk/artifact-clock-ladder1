## 2 关键判定：网关是否定长重打包

原预注册判据（`CV_chunk>0.15 且 CV_len>0.2`）在本批数据上**失效**——因为它取的是"跨 3 个 prompt 的中位数"，
而 P2/P4 两种约束型 prompt 的输出长度天然相同（13 B / 17 B），中位数被压成常数，`CV_len` 必然为 0。
**这是判据设计缺陷，不是数据结论。** 按纪律，正式判定仍为 `INCONCLUSIVE`，不得改判据后宣布通过。

改用**同 prompt 内跨模型**的描述性统计（*事后分析，不能作为闸门结论*）：

| prompt | 输出字节（3 模型） | 内容块数 | **每块文本字节** |
|---|---|---|---|
| P2 | 13 / 13 / 13 | 5 / 5 / 4 | 2.60 / 2.60 / **3.25** |
| P4 | 17 / 17 / 17 | 2 / 3 / 3 | **8.50** / 5.67 / 5.67 |
| P6 | 353 / 386 / 319 | 38 / 27 / 23 | 9.29 / 14.30 / 13.87 |

**若网关按固定字节重打包**，则"每块文本字节"应在模型间恒定、且与输出长度成正比。
实测：同一条 prompt、同样输出字节（P2 的 13 B），块数却是 5/5/4；每块文本字节从 2.60 到 14.30 跨 5.5×。
⇒ **观察到的分块边界与字节数无固定关系，更像 token 边界透传。**

这是目前**最有价值的正面信号**，但它只是描述性的，需要按修正后的判据在新请求上复验（见 `AMENDMENT_2`）。

## 3 两个必须提前处理的污染源

**(a) `first_chunk_bytes` 泄漏模型名长度。**
首块 252 B（`qwen3.5-27b`）vs 258 B（另两个），差值 6 B ≈ 回显模型名的长度差。
这个字段若进 C1，识别的是"模型名字符串长度"，不是包结构。**建议从 C1 移除该特征**，
否则审稿人一眼就能指出这是 trivial 泄漏。

**(b) SSE 封装完全主导字节。**
每条 SSE 行 ~202–244 B，而携带的文本只有 2.6–14.3 B；`sse_overhead_ratio` 实测 0.96–0.99，
且主要由块数决定，与内容无关。⇒ C1 里"封装占比"与"块数"高度共线，二者不能同时作为独立证据。
